# 0003. Count every maildir file as one message

- **Status:** Accepted
- **Date:** 2026-10-23
- **Author:** Helena Rivas (with product-owner agent)
- **Deciders:** Helena Rivas
- **Related:** [#4](https://github.com/hrhelena/elisa-task/issues/4), [#6](https://github.com/hrhelena/elisa-task/issues/6), [#9](https://github.com/hrhelena/elisa-task/issues/9), [0002](0002-no-full-text-indexing-store-headers-only.md), [0007](0007-tolerate-malformed-dataset-entries.md)

## Summary

Every regular file under `maildir/` that parses as an email counts as one message, with no deduplication, for both the
`/status` total and the `/top-senders` ranking. A content hash is stored so deduplication can be added later.

## Context

- The dataset has 150 mailboxes and 517,401 files (counted locally on 2026-10-23).
- `Message-ID` is generated by JavaMail during the export and is unique per file, so it cannot be used as a deduplication key.
- Roughly half of the files are copies of the same email in several folders of one mailbox (`sent`, `_sent_mail`,
  `sent_items`, `all_documents`, ...), and the same email also appears in the sender's and the recipients' mailboxes.
- The task description says "total number of messages processed" and "top senders" without defining duplicates.

## Decision

- One maildir file = one stored row = one message. The `/status` total and the `/top-senders` counts are per file.
- Each row stores `content_sha256`: SHA-256 over the normalized From, To, Cc, Subject, Date and the raw body bytes,
  excluding `Message-ID`, `X-Folder`, `X-FileName` and other export-specific headers. The body is hashed during parsing and not stored.
- The relative file path is the natural key (unique), which makes re-ingestion idempotent.

## Rationale

| Option | Pros | Cons |
|---|---|---|
| Per file, no dedup (chosen) | Literal, simple, matches what was processed, easy to verify with `find \| wc -l` | Inflates counts for people with many folder copies |
| Dedup by `Message-ID` | Trivial | Does nothing: IDs are unique per file |
| Dedup by content hash | Closer to "distinct emails" | Hash definition is a judgment call (whitespace, header variants); harder to explain |

The user chose literal per-file counting. Storing the hash now costs 32 bytes per row and avoids a re-ingest if
dedup is wanted later.

## Consequences

- Positive: counts are reproducible and match the file count minus skipped files.
- Negative: top-senders reflects copies (for example, a message in both `sent` and `_sent_mail` counts twice).
- Follow-ups: content-hash dedup (`COUNT(DISTINCT content_sha256)`) is listed as a README extension.
